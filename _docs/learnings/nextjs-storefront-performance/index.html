Fast multi-store storefronts with Next.js: what we learned

We studied vercel.shop and its open template (template.vercel.shop), Vercel's reference store built on Next.js and Shopify. Then we applied what fits to the Prood storefront (apps/storefront), which serves many stores from one deployment, one per host. This guide records each practice, why it matters, how we applied it, and what tripped us up, so the next project can start where we finished.

Stack Next.js 16.4 with Cache Components and Partial Prefetching · React 19 · a separate commerce API · Turborepo monorepo.

The short version

  1. Give each store its own route tree, keyed by host, so pages are built and cached per store.
  2. Cache catalog reads with tags, and expire the tags when data changes. Don't wait for a timer.
  3. Expire across deployments: the service that changes data tells the storefront which tags to drop.
  4. Use static shells, not loading.tsx: put Suspense inside the page so the header and footer show at once.
  5. Return real 404 status codes. A notFound() inside streamed content still answers 200.
  6. Describe pages with JSON-LD, escaped so it can't break out of its script tag.
  7. Split the sitemap into an index plus files of a few hundred products each.
  8. Serve Markdown to agents: .md URLs, Accept: text/markdown, and llms.txt.
  9. Prefetch on intent: in a grid, upgrade a link's prefetch only when the shopper points at it.
  10. Make optimistic updates survive quick clicks: roll back to the last server answer, and apply only the newest response.
  11. Treat Server Actions as public endpoints: validate them with the same zod schema as the form.
  12. Keep the build independent of the database and API.

1. One route tree per store, keyed by host

Rule
Put the whole app under a [host] root segment and let the proxy rewrite /path to /{host}/path.
Why
Next.js caches a page by its URL. If every store shares /products/mug, nothing about the store is in the cache key, so pages can't be cached safely. With the host in the path, each store's pages are built and cached on their own, the same way vercel.shop caches per market.
How we did it
apps/storefront/proxy.ts, app/[host]/layout.tsx, lib/store-host.ts, lib/tenant.ts
// proxy.ts: the store's route tree lives under its host
url.pathname = `/${host}${pathname === "/" ? "" : pathname}`
return NextResponse.rewrite(url)

// any Server Component or "use cache" function
import { host } from "next/root-params"
const store = await getStore(await host())

Pitfalls

  • host() from next/root-params works in Server Components and inside "use cache", but not in Route Handlers or Server Actions. Those read the Host header instead (our requestHost()).
  • Pass the host into cached functions as an argument. It then becomes part of the cache key, which makes leaking data between stores impossible by construction.
  • Let /api/* pass through the proxy untouched. Route Handlers read the host themselves.
  • Files that must stay at the root, like favicon.ico and icon.svg, need excluding from the proxy matcher.

2. Tagged caches per store

Rule
Every catalog read is a "use cache" function tagged {kind}-{storeId} (products, categories, store). Its time limit is long, because a tag expires it the moment data changes.
Why
A short timer either serves stale prices or hammers the API. Tags give both: pages served from cache in milliseconds, and fresh as soon as a merchant saves.
How we did it
apps/storefront/lib/catalog.ts, packages/types/src/cache-tags.ts
export async function getProductBySlug(storeHost: string, slug: string) {
  "use cache"
  cacheTag(storeCacheTag("products", await tenantIdOrMarketing(storeHost)))
  cacheLife({ stale: 300, revalidate: 3600, expire: 86_400 })
  return unwrap(getCatalogApi(storeHost).GET("/products/by-slug/{slug}", …))
}

Pitfalls

  • Cached reads must not depend on cookies. We split the API client in two: a catalog client that sends only the store host, and a shopper client that forwards cookies and is never cached.
  • Don't cache free-text search. The set of queries never ends, so the cache would only fill up. Listings, sorts, pages and categories are a small set per store, so cache those.
  • Share the tag names in one typed module (STOREFRONT_CACHE_TAGS) so the writer and the reader can't drift apart.

3. Expiring caches across deployments

Rule
The service that changes data expires its own tags, then, after responding, POSTs them to the storefront's /api/revalidate. That request carries a shared secret and a validated list of tags.
Why
revalidateTag() only affects the deployment that calls it. Our API and dashboard are separate apps, so calling it there alone left the storefront serving stale pages.
How we did it
packages/commerce/src/revalidate.ts, apps/storefront/app/api/revalidate/route.ts
// @prood/commerce
for (const tag of tags) revalidateTag(storeCacheTag(tag, tenantId), { expire: 0 })
after(() => revalidateStorefront(tenantId, tags).catch(console.error))

// storefront /api/revalidate
const body = z.object({ tenantId: z.string().min(1), tags: z.array(z.enum(STOREFRONT_CACHE_TAGS)).min(1) })
// Bearer secret compared with timingSafeEqual; 401 or 400 otherwise

Pitfalls

  • Use after() so the merchant's save never waits on the storefront, and give the request a timeout.
  • Compare secrets with timingSafeEqual, and accept only known tags (a zod enum), so the endpoint can't be used to flush arbitrary caches.
  • Audit every write path. Wiring this up exposed two bugs: category changes and inventory changes never expired anything. Store settings that affect the storefront, such as payment integrations, need expiring too.
  • If the call fails, the cache's time limit is the safety net, so keep that limit at an hour or less.

4. Static shells instead of loading.tsx

Rule
Delete loading.tsx from catalog routes. Inside each page, wrap the data-dependent part in <Suspense> with a skeleton shaped like the content, and read params inside that boundary.
Why
loading.tsx swaps out the whole page. A Suspense boundary inside the page keeps the store's header, navigation and footer as a static shell that paints immediately, even for a product that has never been built. That is what makes vercel.shop feel instant.
How we did it
components/commerce/product-page.tsx, components/commerce/collection-page.tsx
export default function ProductDetailPage({ params }) {
  return (
    <Suspense fallback={<ProductPageSkeleton />}>
      <ProductPageContent slug={params.then((p) => p.slug)} />
    </Suspense>
  )
}
Passing params as a promise and awaiting it inside the boundary is the key detail. Awaiting it in the page body would make the whole page wait.

5. Real 404s and unknown stores

Rule
Decide "not found" before streaming starts. Do it in the proxy for known routes, with a global not-found page for unmatched paths, and by redirecting unknown hosts on every render path.
Why
Search engines trust the status code. A soft 404 (a 200 with "not found" text) wastes crawl budget and can get indexed.
How we did it
proxy.ts, lib/catalog-check.ts, app/global-not-found.tsx, lib/tenant.ts

What we found

  • notFound() inside streamed Suspense content answers 200, adding only a noindex tag, because the status was sent with the shell. So the proxy checks document requests for missing products, categories and policy pages, and rewrites them to the store's not-found page.
  • With the root layout under [host], paths that match no route get Next's bare 404. Turning on experimental.globalNotFound and adding app/global-not-found.tsx gives a styled, real 404.
  • A redirect in the layout isn't enough. Layout and page render in parallel. When a host had no store, the page's catalog read threw first and the response became a 500. The fix is to make every catalog read redirect unknown hosts the same way, so all render paths agree.

6. A build that needs nothing running

Rule
With Cache Components, generateStaticParams must return at least one value. For a multi-store app, return a placeholder host that renders as not found.
Why
CI builds without a database or API. If the placeholder is a real store, the build tries to fetch its data and fails, as ours did.
How we did it
BUILD_HOST = "build.invalid" in lib/store-host.ts. The reserved .invalid domain can never resolve, and tenantIdForHost() calls notFound() for it before any lookup.

Pitfalls

  • The Next docs suggest exactly this: "return a placeholder param … then handle it in your page with notFound()."
  • Next also prerenders a Route Handler at a path named sitemap.xml, using a stand-in host of -. Hosts without a dot can't be stores, so the lookup returns null for them without touching the database.
  • Test it: COMMERCE_API_URL=http://127.0.0.1:9 DATABASE_URL=postgresql://u:p@127.0.0.1:9/x next build must pass.

7. Structured data (JSON-LD)

Rule
Add schema.org JSON-LD to every catalog page: Product and BreadcrumbList on products, CollectionPage on categories, and OnlineStore plus WebSite with a SearchAction on the home page.
Why
Rich results in search, and answer engines that can read price and stock without guessing.
How we did it
lib/json-ld.ts, components/layout/json-ld.tsx

Pitfalls

  • Escape < as \u003c. A product named </script>… could otherwise close the tag and run code.
  • Leave out fields the product doesn't have, rather than sending empty ones.
  • Merchant descriptions are HTML. When turning them into plain text, replace block tags with spaces and drop inline tags. Our first version turned <b> into a space and produced "stoneware ." A unit test caught it.

8. Split sitemap and robots.txt

Rule
Serve /sitemap.xml as an index that points at pages.xml and products-N.xml files of 500 products each, with images. Each file fetches only the API pages that exist.
Why
One giant sitemap means one giant request, and it breaks the 50,000-URL limit for big stores. Small files are cached and rebuilt independently.
How we did it
lib/sitemap.ts, app/[host]/sitemap.xml/route.ts, app/[host]/sitemap/[file]/route.ts, app/[host]/robots.txt/route.ts
Fetch the first page of a file, read total, then fetch only the remaining pages. Our first version always fetched 5 pages, even for a store with 30 products.

9. Pages for agents: Markdown and llms.txt

Rule
Every catalog page has a Markdown version. Agents reach it by adding .md to the URL (/index.md for home) or by listing text/markdown first in Accept. /llms.txt lists where those pages are.
Why
AI shopping assistants read text, not layouts. Markdown is a fraction of the size and has no navigation noise.
How we did it
lib/markdown-route.ts, lib/markdown.ts, app/[host]/md/[[...path]]/route.ts, app/[host]/llms.txt/route.ts

Pitfalls

  • Only serve Markdown when it is the first accepted type. Browsers send long Accept lists, and those must still get HTML.
  • Send Vary: accept so caches keep the two versions apart, X-Robots-Tag: noindex so search engines don't index duplicates, and a Link: rel=canonical header pointing at the HTML page.
  • Link HTML pages to their Markdown version with <link rel="alternate" type="text/markdown">. Next's metadata API does this through alternates.types.

10. Prefetch on intent

Rule
In grids, links start with prefetch="auto" and switch to prefetch={true} on pointer enter, touch start or focus.
Why
With Partial Prefetching, "auto" prefetches the shared shell for free. true also fetches the product's own cached content, which is worth doing only once the shopper shows interest. Prefetching every card in a 24-product grid costs 24 requests.
How we did it
packages/ui/src/components/product-card.tsx: one intent state per card, shared by its image link and its title link.
const [intent, setIntent] = useState(false)
const prefetch = intent ? true : "auto"
<div onPointerEnter={showIntent} onTouchStart={showIntent} onFocus={showIntent}>
  <Link href={url} prefetch={prefetch}>…

11. Optimistic cart that survives quick clicks

Rule
Show quantity changes immediately. Keep a reference to the last cart the server confirmed, number each request, apply a response only if it's the newest, and on failure go back to the confirmed cart.
Why
The usual "snapshot, then roll back" breaks with two quick clicks: the second snapshot captures the first click's unconfirmed state, and responses that arrive out of order overwrite newer ones.
How we did it
apps/storefront/components/providers/cart-provider.tsx: confirmedRef, latestRef, and a pending count, so the loading state stays on until every request has settled.
Use functional updates, setCart((current) => …), so quick changes build on each other instead of on a stale closure.

12. Validated Server Actions

Rule
Parse every Server Action's input with zod before doing anything. Reuse the form's own schema, so the server checks exactly what the form checked.
Why
A Server Action is a public POST endpoint. TypeScript types disappear at runtime, and anyone can call it with anything.
How we did it
app/[host]/(checkout)/checkout/actions.ts reuses addressSchema and contactSchema from components/checkout/schemas.ts, including postal-code rules per country.

13. What we chose not to copy

vercel.shop doesWhy we didn't
Shopify Storefront API and Hydrogen helpersProod is its own commerce platform with its own API.
A built-in shopping agentOut of scope. We made the store readable to any agent instead (Markdown, llms.txt, JSON-LD).
No testsOur storefront has 250+ unit tests, and they caught two real bugs while we did this work.
oxlint and the TypeScript 7 previewToolchain churn with no user-facing benefit for us yet.
Per-market routing ([locale])Our partition key is the store host. Locales can be added inside it later.

14. Open items and caveats

  • Cart permalinks (/cart/<variant>:<qty>, to share a ready-made cart) aren't built yet.
  • Universal Commerce Protocol (/.well-known/ucp): skipped until the spec settles.
  • Canonical tags on listings: /products has no canonical, because its sort and page parameters make different pages. Category pages point at their own path.
  • The home page has no skeleton. It is cached per store and fast after the first visit, but a store's very first visit waits for the data.
  • Cold proxy lookups: the proxy's missing-page check has a 1.5-second timeout. A cold first lookup can exceed it, and that request then answers 200 instead of 404. Later requests are correct.
  • prood.com (apps/web) can use the same practices: static shells, JSON-LD, sitemap, Markdown and llms.txt, and prefetch on intent. Per-store routing isn't needed there.

15. Checklist for the next project

  1. Choose the cache partition key (host, locale, market) and make it the root segment, rewritten by the proxy.
  2. Split data access into cached reads (no cookies, key passed as an argument, tagged) and per-user reads (never cached).
  3. Define the cache tags in one typed module, shared by the writer and the reader.
  4. For every write path, expire the tags locally and notify each other deployment through a secret-protected webhook. Test that each write path does it.
  5. Replace loading.tsx with Suspense inside pages. Read params inside the boundary.
  6. Make 404s real: check in the proxy, add a global not-found page, and redirect unknown keys on every render path.
  7. Make generateStaticParams return a placeholder that renders as not found, and build with the database and API unreachable.
  8. Add JSON-LD with < escaped, plus a split sitemap and robots.txt.
  9. Add Markdown versions and llms.txt, with Vary, noindex and a canonical link header.
  10. Prefetch grids on intent ("auto", then true).
  11. Make optimistic UI race-safe, and validate Server Actions with the form's schema.
  12. Measure first and repeat visits in a production build, not in dev.
